# 写优先插队调度器实现逻辑详解

> 源码：`src/Mal.UniversalScada.Core/Services/PriorityScheduler.cs`
> 接口：`src/Mal.UniversalScada.Core/Abstractions/IPriorityScheduler.cs`

---

## 一、设计目标与总体思路

该调度器的核心契约在 `IPriorityScheduler` 中明确：

> 协调所有通道与下位机的周期性轮询采集，并保障用户操作控制下发（写指令）能够享有**绝对最高优先级即时插队执行**。

实现上采用"**每通道独立工作线程 + 双优先级队列**"模型：

- 每个物理通道（如一条串口、一个 TCP 连接）对应一个独立的 `ChannelWorkerLoopAsync` 调度循环。
- 每个循环内部维护一个**无界异步写通道** `Channel<WriteJob>`（高优）和一条**周期读轮询路径**（次优）。
- 写指令通过 `EnqueueWriteAsync` 投递到对应通道的写队列，循环每次迭代都会**先排空写队列再执行读轮询**，从而保证写优先。

## 二、关键数据结构

### 1. 写指令异步通道 —— 写优先的核心载体

```csharp
// PriorityScheduler.cs L32-L33
private readonly ConcurrentDictionary<string, Channel<WriteJob>> _writeChannels
    = new(StringComparer.OrdinalIgnoreCase);
```

每个 `ChannelId` 对应一个独立的 `Channel<WriteJob>`。在启动时（L102-L107）创建：

```csharp
var writeChan = Channel.CreateUnbounded<WriteJob>(new UnboundedChannelOptions
{
    SingleReader = true,   // 只有该通道的工作线程读取
    SingleWriter = false   // 多个 UI 线程可并发写入
});
```

选型要点：

- **无界（Unbounded）**：写指令绝不因队列满而阻塞或丢弃，工业控制场景下写指令宁可堆积也必须全量送达。
- **SingleReader = true**：每个写通道只有一个消费者（该通道的调度循环），避免多读者竞争，性能最优。
- **SingleWriter = false**：允许 UI 层多个操作员/多线程并发下发写指令。

### 2. WriteJob —— 写作业单元

```csharp
// PriorityScheduler.cs L412-L417
private sealed record WriteJob(
    TagNode Tag,
    DeviceNode Device,
    object Value,
    TaskCompletionSource<WriteResult> Tcs,
    CancellationToken Ct);
```

携带目标点位元数据、目标设备、写入值，以及一个 `TaskCompletionSource<WriteResult>`。这是实现"**异步投递、同步等待结果**"的关键——调用方 `await tcs.Task` 挂起，直到调度循环执行完写操作后 `TrySetResult` 唤醒。

### 3. 其它查找表

- `_tagLookup` / `_deviceLookup` / `_drivers`：点位、设备、驱动实例的快速索引，避免每次写指令都遍历配置。
- `_deviceLastPoll`：每个设备上次轮询时间戳，用于周期采集节流。

## 三、写指令插队流程（EnqueueWriteAsync）

`PriorityScheduler.cs` L174-L200 是写优先的入口：

```csharp
public async Task<WriteResult> EnqueueWriteAsync(long tagId, object value, CancellationToken ct = default)
{
    // 1. 校验点位元数据是否存在
    if (!_tagLookup.TryGetValue(tagId, out var tag)) ...
    // 2. 校验点位所属设备
    if (!_deviceLookup.TryGetValue(tag.DeviceId, out var device)) ...
    // 3. 校验目标通道的写队列是否就绪
    if (!_writeChannels.TryGetValue(device.ChannelId, out var writeChan)) ...

    // 4. 构造写作业 + TCS
    var tcs = new TaskCompletionSource<WriteResult>(TaskCreationOptions.RunContinuationsAsynchronously);
    var job = new WriteJob(tag, device, value, tcs, ct);

    // 5. 写入队列插队
    await writeChan.Writer.WriteAsync(job, ct);

    // 6. 挂起等待执行结果
    return await tcs.Task;
}
```

关键点：

- **路由到正确的物理通道**：通过 `tag → device → device.ChannelId` 三级查找，把写作业投递到该点位所在设备所属通道的写队列。这是必要的——SCADA 中一条物理链路同一时刻只能收发一帧报文，写指令必须与读轮询共用同一通道。
- **RunContinuationsAsynchronously**：避免 `TrySetResult` 时同步执行调用方的 continuation（可能造成栈式递归），保证调度循环不被调用方逻辑阻塞。
- **调用方语义为同步等待**：UI 点击"下发设定值"按钮后能拿到真实执行结果（成功/失败/耗时），符合控制场景对"指令是否真正送达下位机"的强确认需求。

批量写 `EnqueueBatchWriteAsync`（L203-L223）只是对单点写的并发封装：用 `Task.WhenAll` 并发投递多个 `EnqueueWriteAsync`，每个作业独立进入各自通道队列。

## 四、调度循环 —— 写优先的执行核心

`ChannelWorkerLoopAsync`（L243-L318）是整个写优先机制的灵魂。每个通道一个，结构如下：

### 第 0 步：初始化

L250-L267：自动打开通道链路，初始化所有设备 `lastPoll = DateTime.MinValue`（促使首轮立即采集一次）。

### 主循环（while !ct.IsCancellationRequested）

每次迭代分两个阶段，**严格保证写在前读在后**：

#### 阶段 1：排空写队列（最高优先级）

```csharp
// L276-L279
// 1. 最高优先级：检查并排空写指令队列
while (writeChan.Reader.TryRead(out var writeJob))
{
    await ProcessWriteJobAsync(channel, writeJob);
}
```

用 `while + TryRead` **一次性排空**当前队列中所有积压的写作业。`TryRead` 是非阻塞的——有则取、无则立即返回 false。这保证只要循环一进入这一步，所有已积压的写指令都会被**连续、无中断**地执行完毕，才会进入读轮询阶段。

#### 阶段 2：周期采集轮询（次优先级）

```csharp
// L284-L303
foreach (var dev in devices)
{
    // ★ 再次检查是否有突发的写指令插队
    if (writeChan.Reader.TryRead(out var emergencyWrite))
    {
        await ProcessWriteJobAsync(channel, emergencyWrite);
    }

    // 检查轮询间隔
    int pollInterval = dev.DefaultPollIntervalMs > 0 ? dev.DefaultPollIntervalMs : 100;
    if (!_deviceLastPoll.TryGetValue(dev.DeviceId, out var lastPoll) ||
        (now - lastPoll).TotalMilliseconds >= pollInterval)
    {
        _deviceLastPoll[dev.DeviceId] = now;
        await PollDeviceTagsAsync(channel, dev, ct);
    }
}
```

这里有**第二道插队关卡**：遍历每个设备准备读取前，**再 `TryRead` 一次写队列**。即使阶段 1 已排空，但在阶段 1 执行期间或阶段 2 遍历到下一个设备的间隙，UI 层可能又投递了新的写指令。这一次检查保证写指令最长等待时间 ≤ 一个设备的读周期，实现"准实时插队"。

周期节流用 `_deviceLastPoll` 时间戳 + `DefaultPollIntervalMs` 判断是否该轮询该设备，未到间隔则跳过（但写插队检查依然执行）。

#### 阶段 3：微休眠

L306：`await Task.Delay(10, ct)` 降低 CPU 空转，同时 10ms 粒度极小，保持高写响应。

### 异常处理

- `OperationCanceledException`：正常退出。
- 其它异常：记日志 + `Task.Delay(100)` 短退避后继续循环（不让单次通信故障拖垮整个调度）。

## 五、写作业执行（ProcessWriteJobAsync）

L323-L364：

```csharp
private async Task ProcessWriteJobAsync(IChannel channel, WriteJob job)
{
    var sw = Stopwatch.StartNew();
    try
    {
        // 1. 查找该设备绑定的协议驱动（Modbus/S7/CustomSerial）
        if (!_drivers.TryGetValue(job.Device.DeviceId, out var driver)) ...;

        // 2. 确保通道连通（断线重连）
        if (channel.State != ChannelState.Connected)
            await channel.OpenAsync(job.Ct);

        // 3. 执行驱动写入
        var writeResult = await driver.WriteTagAsync(job.Tag, job.Value, job.Ct);

        // 4. 成功后回写实时数据总线内存快照
        if (writeResult.IsSuccess)
        {
            _dataBus.PublishSnapshot(new TagValueSnapshot { ... });
        }

        // 5. 唤醒等待的调用方
        job.Tcs.TrySetResult(writeResult);
    }
    catch (Exception ex)
    {
        job.Tcs.TrySetResult(WriteResult.Failed(..., ex.Message, sw.ElapsedMilliseconds));
    }
}
```

要点：

- **断线自愈**：写执行前检查通道状态，断开则重连，避免因临时链路中断导致写指令失败。
- **写后回写快照**：写成功后立即 `PublishSnapshot` 更新 `RealtimeDataBus` 内存值。这样 UI 无需等下一轮读轮询就能立即看到下发值反映，状态一致性更好。
- **Stopwatch 计时**：记录每条写指令耗时，便于性能监控与超时诊断。
- **异常兜底**：任何异常都通过 `TrySetResult(Failed)` 唤醒调用方，绝不留下挂起的 `tcs.Task` 造成调用方永久阻塞。

## 七、写优先机制的两道插队关卡总结

整个调度循环的优先级保障靠**两道关卡**实现：

| 关卡 | 位置 | 作用 | 最大写等待延迟 |
|------|------|------|----------------|
| 第 1 道 | 循环开头 `while(TryRead)` 排空 | 每轮开始先把所有积压写一次性发完 | ≤ 一次完整轮询周期 |
| 第 2 道 | 每个设备读取前 `TryRead` 单次 | 读轮询中途也能被写打断 | ≤ 单个设备读取耗时 |

这意味着：即使一轮读轮询很长（多设备、大批量），写指令最长也只需等"当前设备这一帧读报文返回"即可插入执行，而非等整轮读完。对工业控制而言，这种"准实时插队"已经足够保证控制下发的及时性。

## 八、启动与停止

### 启动（L56-L133）

1. 加载工程拓扑（通道/设备/点位）。
2. 为每个启用通道：创建 `IChannel` + `Channel<WriteJob>` 写队列 + 实例化该通道下所有设备的协议驱动。
3. **每个通道启动一个独立 `Task.Run(ChannelWorkerLoopAsync)`** —— 多通道并行调度，通道间互不阻塞。

### 停止（L136-L172）

取消令牌 → `Task.WhenAll` 等待所有工作线程退出 → 关闭所有物理通道 → 清理字典。

## 九、整体流程图

```
UI 点击"下发"
    │
    ▼
EnqueueWriteAsync(tagId, value)
    │  tag→device→ChannelId 路由
    ▼
_writeChannels[ChannelId].Writer.WriteAsync(job)   ← 写作业入队
    │
    │ (调用方 await tcs.Task 挂起)
    ▼
═══════════ 该通道的 ChannelWorkerLoopAsync ═══════════
    │
    ├─ 阶段1: while(TryRead) 排空写队列 ──► ProcessWriteJobAsync
    │                                          ├─ driver.WriteTagAsync
    │                                          ├─ 回写 RealtimeDataBus
    │                                          └─ tcs.TrySetResult(唤醒调用方)
    │
    ├─ 阶段2: foreach 设备:
    │         ├─ ★TryRead 再次插队检查
    │         └─ 到周期? → PollDeviceTagsAsync (批量读)
    │
    └─ Task.Delay(10)
```

## 十、设计亮点小结

1. **写优先靠"队列 + 两道检查"而非线程抢占**：不依赖线程优先级或锁竞争，结构简单可靠，跨平台行为一致。
2. **无界 `Channel<WriteJob>`**：写指令永不丢失/阻塞，符合工业控制"宁可堆积不可丢弃"原则。
3. **`TaskCompletionSource` 解耦投递与执行**：调用方拿到真实的同步结果，又能让执行在专用调度线程上完成。
4. **每通道独立循环**：天然隔离不同物理链路，一条慢通道不影响其它通道的写响应。
5. **写后回写快照**：UI 即时反馈，无需等读轮询闭环。
6. **断线自愈 + 异常兜底**：写执行健壮，不会因临时故障造成调用方永久挂起。

这套机制在保证读采集持续运转的同时，让控制写指令在亚轮询周期内插队执行，是 SCADA/HMI 上位机调度引擎的典型且实用实现。
